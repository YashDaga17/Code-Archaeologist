# Proposed Architecture  

 *Figure: High-level architecture. A Next.js frontend on Databricks Apps sends queries to a model-serving endpoint backed by a foundation LLM; code context from Entire Checkpoints/Graph informs analysis.* Our solution runs the Next.js UI and API routes as a Databricks App (Node.js/React) integrated with Databricks compute.  In this design:  

- **Next.js UI (Databricks App)** – Hosts the dashboard for reviewing AI-generated commits.  Using Databricks Apps allows a React/Next.js frontend (Node.js) to run serverlessly with built-in access to Databricks services.  We leverage the injected service credentials (`DATABRICKS_CLIENT_ID`, `DATABRICKS_SECRET`, etc.) provided in the Databricks Apps environment so our code can fetch OAuth tokens and call Databricks REST endpoints directly.  
- **Next.js API (Serverless Functions)** – Implements backend logic.  For example, a request from the UI triggers a Next.js API route that: reads the relevant Entire Checkpoint JSON (captured via `entire checkpoint explain`), sends it to a Databricks LLM endpoint for intent extraction, and then runs a Graph CLI query to verify claims.  Because the frontend runs inside Databricks Apps, these API routes can securely invoke Databricks’s Model Serving or Foundation Model APIs without external middlemen.  
- **Databricks Foundation Model / Serving** – We use Databricks-hosted LLMs (e.g. the Llama 3 or GPT family via the Foundation Model APIs) for NLP inference.  The UI/API will call Databricks’s pay-per-token endpoints for chat or completion (e.g. POST to `/serving-endpoints/{name}/invocations`) using a service principal OAuth token.  We operate in *priority mode* (“pay-per-token priority”) to keep latency low for interactive use.  For instance, the API might send the entire Checkpoint transcript to a GPT model and ask “What requirements or tests are missing?” then parse the LLM’s JSON reply.  
- **Databricks Storage & Processing** – The NLP step can be done in-stream (synchronous) or via Spark jobs.  For scale, we could feed checkpoints into a Databricks notebook or job, apply a Foundation Model or even Spark NLP libraries, and write structured results (e.g. identified tasks) to a Delta table.  The Next.js UI then queries that table (or reads back the immediate response) to update the dashboard.  This avoids building a heavy custom API: Databricks’s model-serving endpoint itself becomes the “backend” for inference, and Next.js simply queries Databricks (via JDBC/SQL or REST) for results.  
- **Entire CLI and Graph** – The user’s repository is mirrored and “Entire” is enabled, so each agent-assisted commit creates a checkpoint.  We use `entire checkpoint list` and `entire checkpoint explain <ID>` to retrieve the session context (prompts, transcripts, files changed).  When the LLM output claims a missing feature (e.g. “no unit tests for function X”), we automatically invoke the Entire Graph CLI: for example, running `entire graph find X` or `entire graph impact` on the codebase to see if that feature or tests exist.  This semantic-graph verification grounds the AI’s assertion in actual code.  The combined results (LLM guess + graph evidence) are shown in the UI with links to code locations.  

This decoupled design makes the solution **modular**: the UI, NLP model, and graph analysis each run in separate components (Next.js front/API, Databricks ML, Entire CLI), communicating via well-defined interfaces (JSON, REST, or tables).  For example, if the noon curveball changes requirements, we can simply update the model prompt or add a new query to Entire Graph without reworking the entire stack.  

## Parsing Entire Checkpoint Data  

We rely on Entire’s metadata and transcript capture for context.  Each checkpoint consists of a `metadata.json` plus session folders containing `full.jsonl` transcripts.  Using the CLI we can emit this data as JSON (e.g. `entire checkpoint explain <id> --json`), or read the raw `.entire/checkpoints` refs on disk.  We extract key fields like the **intent prompt**, **files_touched**, and the agent’s **transcript** (the `full.jsonl` chat log).  In our pipeline:  

1. **Fetch Checkpoint JSON.** On demand, the Next.js API calls `entire checkpoint explain <id>` and parses the output. This yields the original user prompt, the AI agent’s exchanges, and which files changed in that commit.  
2. **Extract Intent and Tasks.** We feed the combined prompt + transcript into the Databricks LLM (e.g. as a single prompt: “Given this coding session transcript, list any features or requirements not yet implemented.”).  The LLM returns structured output (JSON with fields like `missing_features`).  
3. **Ground in Code with Graph.** For each item the LLM flags (e.g. “no logging for X”), we run an Entire Graph query to confirm.  For instance, `entire graph diff` or a semantic query can check if any code or tests mention that feature.  This double-check mitigates hallucinations.  We display any matching code lines or note “none found” to close the loop.  

By layering LLM inference on top of Entire’s structured session data, we turn the raw agent transcripts into actionable insights.  This addresses the “Review implementation vs intent” requirement: the UI shows the original intent prompt, what code was written, and any **gaps** identified. 

## Databricks NLP Integration  

For the NLP step, we leverage Databricks’s Managed LLM services: either a **Model Serving Endpoint** hosting an open model or the **Foundation Model APIs** (e.g. `databricks-meta-llama-3-3-70b-instruct` or Databricks’s GPT endpoints).  The Next.js API obtains an OAuth token for a Databricks service principal (using the injected `DATABRICKS_CLIENT_ID/SECRET/HOST` in the app environment) and makes a POST to `/serving-endpoints/{name}/invocations` with the prompt content.  We set `temperature=0` and use **priority mode** to ensure fast, consistent latency.  The API then parses the JSON response.  

Because the question of integrating with Next.js was raised, our plan is to **avoid building a large custom API** by using Databricks’s native serving.  In practice, we deploy our Next.js app on Databricks Apps so it can call Databricks endpoints in-app.  The blog on “Databricks Apps with React” shows exactly this pattern: user queries flow from the React UI through a Databricks-hosted model-serving endpoint.  In our code, the Next.js backend calls the same internal endpoint that hosts the LLM, so data doesn’t exit the Databricks network.  This means results appear in the UI as soon as they are computed, without an extra intermediary.  

If needed for very large-scale checkpoints, we can also leverage Spark. For instance, a Databricks notebook could run NLP jobs across many sessions (e.g. using Spark NLP or the same Foundation Model in a distributed way) and write the outputs to a Delta table or MLflow experiment.  The Next.js UI would then simply query that table (via Databricks SQL or a small API call) for the latest analysis of each checkpoint.  This streaming/storage approach ensures the UI always has up-to-date data without hammering an external API.  

## Verification with Entire Graph  

Entire Graph is used to verify the AI’s conclusions against the actual codebase.  For example, if the NLP layer says “requirement X not implemented,” we run a graph query like `entire graph find --function X` or `entire graph impact --symbol X` to see if any code references exist.  This automated check provides concrete evidence: if Graph finds related code or tests, we mark the requirement as “already done”; if not, we list it as truly missing.  The official guidelines even emphasize this: *“Use Entire Graph for investigation, impact analysis before risky changes and a final semantic-diff review”*.  

Concretely, our Next.js backend might execute a shell command `child_process.exec('entire graph serve ...')` or use an npm package for Entire (if available) to programmatically run the graph query and parse its JSON output.  The results (e.g. a boolean or code snippet) are combined with the LLM’s output and returned as part of the API response.  This way, the UI displays only those missing tasks that truly lack coverage, reducing false positives.  

## Real-Time Frontend Integration  

To keep the UI responsive, we design for streaming and asynchronous updates.  The Next.js frontend uses webhooks or polling on its API endpoints.  When a user selects a checkpoint, the frontend calls a Next.js API route that immediately begins the NLP/Graph workflow.  We use **async/await** to stream partial results (if supported by the model-serving API) or at least quickly return a placeholder “Analysis in progress…” and update when ready.  Because Databricks Apps are serverless, we avoid a fixed server bottleneck: each analysis request can spin up Databricks compute on demand.  We also take advantage of **Databricks Unity Catalog** and caching: if multiple users analyze the same checkpoint, we cache the LLM results in a Delta table so repeat calls are instant (as suggested by Databricks best practice for AI apps).  

Authentication and security are handled via M2M OAuth (service principal) as per Databricks documentation.  This means our Next.js API can securely call any Databricks API (Model Serving, Unity Catalog, etc.) without exposing tokens.  In short, by co-locating the Next.js app and Databricks services, we achieve near-real-time flow: the UI triggers a Databricks LLM call and immediately reads the output, all within the Databricks cloud.  

## Demo Strategy and Noon Curveball Readiness  

For the hackathon demo, we will prepare a **golden scenario** with a known checkpoint JSON and expected missing tasks.  We’ll hardcode or seed this checkpoint in Databricks to ensure the LLM output is predictable (avoiding last-minute hallucinations).  The demo script will show: enabling Entire on a repo, making a commit, running `entire checkpoint list`, selecting a checkpoint, and then the dashboard instantly highlighting the intent vs. code gap.  

Critically, our modular design directly addresses the judges’ Noon Curveball requirement.  Because we separate concerns, if the curveball changes (e.g. “now require a REST API instead of JSON output”), we only swap out or extend the affected component.  For example, if we need a different output format, we update the JSON schema generator.  The guidelines explicitly say to “stop implementation, … use your Checkpoint and Entire Graph to assess impact, then adapt”.  Our solution meets this by preserving the checkpoint context in Databricks and by having each pipeline stage swappable: we can test alternative LLM prompts, adjust Graph queries, or rewrite the small Next.js handler without rewriting the core UI.   

In summary, by integrating Entire’s checkpoints and graph analysis with Databricks’s Foundation Model APIs and Apps hosting, our architecture provides an **innovative, end-to-end solution**.  It delivers live verification of AI-assisted code handoffs, scales to enterprise workloads with Spark, and can be adapted on-the-fly to meet any new requirement (as the Noon Curveball demands), all while giving developers a clear, interactive UI to review intent vs. implementation.
